## 1. プロジェクトの目的と概要

### 1.1 目的
部品の使用率による**異常検知で、交換率が高いと検知された「製品(機種)× 部品番号」**について、その部品を交換した修理(全世界)のコメントに、**どのような故障の種類が多いか(特定の故障の傾向があるか)**を調べ、表と中立的な説明文(日本語)で示す。

- 交換部品は、コメントとは別の列のデータから取る。コメントには交換部品はほとんど書かれていない。
- 異常がなければ「目立った差は見られない」と書くのが正しい結果。無理に異常を探さない。
- 件数の比較は構成比(割合)の比較で、故障率ではない(出荷台数・生産台数のデータが無い)。

### 1.2 処理の流れ
```
[修理データ CSV(全世界、製品×部番で抽出済み、1行=1修理)]
 → (1) 読み込み・内部キー・言語判定                 Python
 → (2) 分類(故障の種類。Dify 経由の LLM)           会社PC の Dify
 → (3) シリアル変換結果の結合・使用期間の計算        Python(変換そのものは会社PCの別ツール)
 → (4) 製品×部番ごとに集計・比較・注目点の判定        Python(決まったルール)
 → (5) 定型文のレポート + (任意)Dify での要約文
```

### 1.3 解析の観点
1. 全体の傾向(故障の種類の構成比と、偏りの大きさ)← **主な問いに答える観点**
2. 最近の修理(実行日の前月までの6か月)vs それ以前
3. 使用期間(受付日 − 製造年月)。12か月以内 vs それ以降
4. 製造ロットへの集中(1ロットごと + 隣り合う3ロットのまとまり)

## 3. 確定している仕様(要点。詳細と ID は要件定義書)

### 3.1 入力・分類
- 1行=1修理。**修理IDが重複しても別の修理**として扱い、行番号の内部キー `rec_key` を付ける(I-02)。
- 必須値が空・受付日が読めない・製品種別がコード体系に無い行は除外し、理由を記録(I-05)。
- 日本(CMJ)も海外も**同じプロンプト**で分類(G-05)。日本語・英語・中国語・韓国語。
- 1修理につき: 故障の種類の一覧(source: user/repair/internal)、主な故障1つ、環境要因、情報量、原文の抜き出し+日本語訳(G-06)。
- **修理者の所見を優先**。再現しなかったユーザ申告も故障の種類に含める。再現・メーカー責任・代表故障は判定しない(G-07、G-09)。
- 主な故障: 修理者・内部の所見の最初 → ユーザ申告の最初 → 判定不能(G-08)。
- 読めない修理は推測しない。部品名だけの記載からも推測しない(G-13)。
- **交換部品の情報は LLM に渡さない**(G-31。渡すと「その部品の修理だからその部品の故障」になり、調べる意味が無くなる)。
- 内部コメントは渡す。CMJ だけ既定で渡さない(設定で変更可。G-12)。
- Dify のエラー: バッチ → 失敗した修理だけ1件ずつ最大2回 → それでもだめなら「分類不可」として先へ進む(G-18〜G-19)。送る内容を変える対策はしない(G-24)。
- 「判定不能」(読めない)と「分類不可」(Dify の都合)は別。どちらも比較の分母から除く(G-20〜G-21)。
- キャッシュ: 販社+修理ID+受付日+渡したコメントのハッシュ。コード体系・プロンプト・内部コメントの設定が変われば別(G-16)。

### 3.2 シリアル変換(別ツール)と結合
- 変換は会社PCの別ツール。解析側は**変換結果 CSV を分類の後に結合**する(第6節)。キーは**製品名 + シリアル + 受付日**(S-11)。
- 既知のタイプ: type1(頭3桁の表引き、全機種共通の表)/ type2(頭2桁 01〜96、1つ=1か月、8年周期、起点は全機種共通)/ type3(頭2桁、機種ごとの開始月が 01、96 で一周することもある)/ prefix2_only・prefix3_only(年月は分からないが、頭桁の順=製造の順)。周期のある方式は「受付日以前で最も近い候補」。
- 変換ツールの入力: CSV(UTF-8)と Excel。解析側に渡すのは CSV。生産台数のデータは無い。

### 3.3 解析
- 実行日を基準日にする。直近は実行日の月を含めず前月までの6か月(A-07)。
- 2群の比較: カイ二乗(全体)、フィッシャー(コードごと)+ Benjamini-Hochberg 補正(A-09)。
- **注目点**: 両群30件以上、補正後 p<0.05、差10ポイント以上かつ高い側で5件以上(A-14)。「その他(少数)」は注目点にしない。
- ロット: 1ロット5件以上で比較。隣り合う3ロットのまとまりでも比較(A-15d)。補正は**全ロットまとめて**(A-15a)。件数の偏りは参考扱い(生産台数が無い)。
- 全体の偏り: 最多の割合・上位3つ・80%に必要な種類の数。50%以上「集中」、30%未満「偏りは小さい」(A-05a)。
- 代表事例は、比べた群で割合が高い注目点だけ(T-08)。「増加」「多発」は使わない(T-04)。
- 他の部品・他の製品との比較は**保留**(比較データを渡せない。1年運用後に必要なら追加)。

### 3.4 実行
- 対話式(`python anomaly_cli.py`): 段階0 再開の確認 → 1 入力 → 2 分類の準備 → 3 分類 → 4 シリアル変換結果 → 5 設定 → 6 解析 → 7 要約 → 8 完了。n で終了し、次回再開できる(U-03〜U-05)。
- `run --input ... --yes` で質問なし(U-06)。

## 5. これまでに発生した問題と解決方法

| 問題 | 解決 |
|---|---|
| 販社によって修理IDが重複し、別の修理なのに同じIDになる | 行番号の内部キー `rec_key` で扱う。結合・キャッシュ・評価は販社名+修理ID+受付日を使う |
| シリアル変換表は会社PCでしか準備できない | 変換を別ツール(会社PCで実装)にし、解析側は変換結果を結合するだけにした。Mac で作った変換表の読み込みのコードは削除 |
| v2 の codebook.py が v2 専用の `claim_reproduction_statuses` を必須にしていた | 任意の項目に変更 |
| 1ロットの修理件数が少なく、10件の条件では比較できない | 5件に下げ、隣り合う3ロットのまとまりでの比較を追加。5件では極端な集中しか拾えないことを数値で示して合意 |
| ロットごとに補正すると、ロットが多いほど偶然の差が注目点になりやすい | 全ロットまとめて補正するように変更(判定は厳しめ) |
| 割合が下がった側の故障にも代表事例を出していた(構成比の影響で下がっただけのことが多い) | 比べた群で高い注目点だけに事例を出し、構成比の注記を付ける |
| 交換部品から故障を推測すると解析の意味が無くなる | 交換部品の情報を LLM に渡さない(G-31)。テストで確認 |
| `init` で作った `.env` の初期値のまま実行すると、存在しない宛先に接続して長く待つ | 初期値のままなら接続せずにエラーにする |
| テストの子プロセスが Mac のフォルダに `__pycache__` を作った | 子プロセスに `PYTHONDONTWRITEBYTECODE=1` を渡す。作られたものは削除 |
| ファイルの送信と編集を同時に実行し、古いファイルが Mac に送られた | 編集 → 送信 → md5 で一致確認、の順に必ず1つずつ行う |
| デスクトップアプリとの接続が途中で切れる | 作業環境(`/mnt/user-data/outputs/IR_rep_categorize_anomaly`)で作り、接続後に Mac へ送って md5 で確認 |
| 何度か、テストの期待値の方が間違っていた(架空の頭桁の計算、閾値による判定) | コードではなくテストを直した(コードの判定は要件どおり) |

## 8. 開発上の注意点と、ユーザの希望する進め方

### 8.1 ユーザの基本ルール(Cowork 全体ルール)
- 回答は日本語。
- **指示されていないファイルは編集・削除・リネーム・上書きしない**。削除・上書きの前は、対象と内容を示して承認を得る。
- 作業範囲は選択されたプロジェクトフォルダの中だけ。
- 新規ファイルは `YYYYMMDD_説明.拡張子`(既存の命名規則があればそちら)。
- **複数ステップの作業は、着手前に簡単な計画を示して承認を得る**。不明な点は推測で進めず質問する。
- **AskUserQuestion ツールは使わない**(質問は文章で)。
- 長い文章・資料・コードはファイルに保存し、保存先を伝える。
- 確認したことと推測を混ぜない。根拠の無い部分は「未確認」と書く。
- 前提情報のファイルを更新したら、どこを変えたか報告する。

### 8.2 この開発の進め方(合意済み)
- **Mac には実データが無い**。Mac で要件定義・架空データ・テスト・ロジックを作る。会社PC(GPT)は実データでの実行・Dify 構築・調整・シリアル変換ツールの実装を行う。
- **情報は Mac → 会社PC の一方向**。会社PCからは、人が手でメモできる短い情報だけが戻る。実データの内容は戻らない(架空の例に言い換えてもらう)。
- 会社PC側は `src/`・`tests/` を変えない。変えてよいのはローカル作業フォルダだけ。
- 要件には ID を付け、テスト名に ID を入れる。要件を変えたら要件定義書の版と履歴を更新する。
- 段階ごとに、テストが通った状態で Mac のフォルダに反映し、md5 で一致を確かめる。
- Python 3.13 以上(会社PCは 3.15)。3.14 以降だけの機能は使わない。Mac 側の作業用環境は 3.10 なので、3.10 でも動く書き方にしておくと確認しやすい。
- 依存ライブラリ: pyyaml、requests、python-dotenv、openpyxl、pandas、scipy(会社PCで使用可と確認済み)。uv は前提にしない。

### 8.3 解析の考え方(ユーザの希望)
- **中立**: 異常を無理に探さない。何が注目点かは Python の決まったルールで決め、LLM は分類と文章化だけ。
- 説明文は、数値と決まった文型で書く。原因を推測しない。
- 判定が厳しくなる方向(偶然の差を拾わない)を優先する。閾値を下げる提案をするときは、検出できる範囲を数値で示してから相談する。
- 文書は短い文の平易な日本語で書く(既存の要件定義書の文体に合わせる)。
