## 1. 目的と範囲

### 1.1 目的

部品の使用率による異常検知で抽出された「製品(機種)× 部品番号」の修理データ(全世界)について、

1. 修理データを、故障の種類(v2 と同じコード体系)で分類する
2. 製品×部番ごとに、次の観点で故障の種類の傾向を集計・比較する
   1. 全体
   2. 最近の修理 vs それ以前(受付日)
   3. 使用期間(受付日 − 製造年月)
   4. 製造ロットへの集中
3. 結果を表と中立的な説明文(日本語)で示す

- **主な問い**(2026-11-05 ユーザ確認): 異常検知で交換率が高いと検知された部品について、**その部品を交換した修理のコメントに、どのような故障の種類が多いか(特定の故障の傾向があるか)**。観点1(全体の傾向と偏りの大きさ、A-05a)がこの問いに答え、観点2〜4は、その傾向がいつ・どの製造ロットで変わったかを補う。
- 交換部品(部品番号)は、コメントとは別の列のデータから取る。コメントには、交換部品はほとんど書かれていない。
- 異常がなければ「目立った差は見られない」と書くことを、正しい結果とする。
- 件数の比較は**構成比(割合)の比較**であり、故障率ではない(出荷台数・生産台数のデータが無いため)。

### 1.2 範囲外

- 修理者が現象を確認できたか(現認)、メーカー責任 YES/NO、代表故障の判定(v2 の機能)
- 他の部品・他の製品との比較(「この部品だから多い故障か、その製品の修理ではもともと多い故障か」の区別)。**保留**(2026-11-05): 比較用のデータは渡せないため。まずは比較なしで完成させ、1年ほど運用してから、必要なら追加する
- 同じ修理で一緒に交換された部品の解析(入力が対象部品の行だけのため)
- 製造時期(最近製造 vs それ以前)の比較(使用期間の解析に置き換えた)
- 故障率(件数 ÷ 台数)の計算

## 3. 全体の流れ

```
[入力CSV: 製品×部番で抽出済み、1行=1修理]
  ↓ (1) 読み込み・列の対応づけ・内部キー・言語判定      input_loader / lang
  ↓ (2) 分類(キャッシュに無いものだけ Dify へ)         classify(llm_request / dify_client / llm_response / cache)
[分類結果: classifications / failures / environments]
  ↓ (3) シリアル変換結果の結合・使用期間の計算          serial_merge
        (変換そのものは別ツール。会社PCで、入力 CSV などを変換しておく)
  ↓ (4) 製品×部番ごとに集計・比較・注目点の判定          analysis(stats / findings)
[表 + 注目点 JSON]
  ↓ (5) 説明文: 定型文(必須)+ Dify の要約(任意)       report
[Excel + Markdown]
```

- 「何が注目点か」は Python が決まったルールで決める(A-14)。LLM は文章にまとめるだけで、データから異常を探させない。

## 4. 入力

- I-01: 入力は CSV(UTF-8、BOM の有無どちらも可)。列の対応づけは `input_columns.yaml` で指定する。

| 内部名 | 内容 | 必須 |
|---|---|---|
| `repair_id` | 修理ID | 必須 |
| `model` | 製品名(開発コード)。「製品×部番」の製品はこの単位 | 必須 |
| `product_type` | 製品種別(ML / LENS / DC。コード体系の選択に使う) | 必須 |
| `part_no` | 部品番号 | 必須 |
| `serial` | シリアル | 列は任意。値は空欄可 |
| `received_date` | 受付日 | 必須 |
| `sales_company` | 販社名 | 必須 |
| `user_comment`, `repair_comment`, `internal_1`, `internal_2` | コメント | 列は必須、値は空欄可 |

- I-02: 入力は 1行 = 1修理とする。**修理IDが重複していても、別の修理として扱う**(販社によっては、同じ修理IDで別の修理があるため)。
  - 読み込み時に、行ごとの内部キー `rec_key`(6桁の連番、例: `000123`)を付ける。Dify への受け渡し・結合・出力はすべて `rec_key` で行い、元の修理IDは列として残す。
  - 修理IDが重複している行の件数を、実行メタ情報に記録する(エラーにはしない)。
- I-03: 1つの入力ファイルに、複数の「製品×部番」の組み合わせが入っていてよい。解析は組み合わせごとに行う。
- I-04: 受付日は `YYYY-MM-DD`、`YYYY/MM/DD`、`YYYY/M/D`、Excel の日付シリアル値を受け付ける。
- I-05: 次の行は処理対象から外し、理由別の件数を実行メタ情報に記録する(理由は上から順に判定し、最初に当てはまったもの)。
  - 必須の値(`repair_id`・`model`・`product_type`・`part_no`・`sales_company`・`received_date`)のいずれかが空(`missing_<項目名>`)
  - 受付日が読めない(`invalid_received_date`)
  - `product_type` がコード体系に無い(`unknown_product`)
  - `rec_key` は除外した行も含めた行番号で付けるため、除外があっても他の行の `rec_key` は変わらない
- I-05a: 除外の理由を、実行した人がその場で分かるようにする。
  - `classify` と対話式(段階1)は、実行フォルダに `excluded_rows.csv` を書く。列: `rec_key`、`row_number`、`repair_id`、`sales_company`、`reason`、`reason_name`(日本語の理由)、`value`。`value` は、`invalid_received_date` なら受付日の値、`unknown_product` なら製品種別の値、それ以外は空。除外が無くても列名だけのファイルを書く。
  - 画面には、理由別の件数を出す。`invalid_received_date` と `unknown_product` は、値の例を件数の多い順に5つまで出す(例: `除外: コード体系に無い製品種別 120 件(値の例: 'ml' 100件, 'Lens' 20件)`)。
  - すべての行が除外された場合は、その旨の注意を出す。
  - `merge-serial` は画面の表示だけを行う(一覧のファイルは書かない)。
- I-06: シリアルは全角を半角にそろえ(NFKC)、前後の空白を除き、英字は大文字にそろえる。シリアルの列が入力に無い場合はエラーにせず、すべて空として扱う。

## 5. 分類

### 5.1 言語

- G-01: 日本語・英語・中国語・韓国語のコメントを分類できること。
- G-02: 言語は、LLM に渡すコメントの文字種から Python で判定し、`lang` 列に入れる。
  - ハングルを含む → `ko`、ひらがな・カタカナを含む → `ja`、漢字を含む(かな無し)→ `zh`、ラテン文字を含む → `en`、文字が無い → `none`
  - 複数に当てはまる場合は上の順で先に当てはまったもの
- G-03: コード一覧は日本語のまま LLM に渡す。

### 5.2 日本と海外

- G-04: 日本と海外は販社名で区別する。日本の販社は `CMJ`(`settings.yaml` の `japan_sales_companies`)。
- G-05: 日本のデータも、海外と**同じプロンプト**で分類する。

### 5.3 LLM に渡す内容

- G-31(2026-11-05 追加): **交換部品の情報(部品番号など)は LLM に渡さない**。部品から故障を推測させると、「その部品を交換した修理だから、その部品の故障」という分類になり、同じ部品の修理に見られる故障の傾向を調べる意味が無くなるため。LLM にはコメントだけを渡す(G-25)。
- G-12: 内部コメント(内部1・内部2)は LLM に**渡す**。ただし、`settings.yaml` の `internal_comment_excluded_sales_companies` にある販社は渡さない。**既定値は `[CMJ]`**。
- G-10: ユーザコメント・修理者コメント・内部1・内部2 のいずれかが空欄なのは普通のこととして扱う(空欄の列があってもエラーや警告にしない)。
- G-11: LLM に渡すコメントがすべて空欄の修理は Dify に送らず、Python で次の結果にする: `failures` 空、`primary_code` = 判定不能コード(`role: unknown`)、`info_level` = `none`。
- G-25: Dify ワークフロー(分類用)への入力変数は次の3つ(v2 の R-30 と同じ形)。
  - `product_name`: 製品種別の表示名
  - `code_list`: コード一覧(`コード | 名称 | 説明文`。responsibility は含めない)
  - `records`: 次の要素の JSON 配列(文字列にして渡す)。渡さないコメントはキーごと省く

```json
{"rec_key": "000123", "user_comment": "...", "repair_comment": "...",
 "internal_1": "...", "internal_2": "..."}
```

- G-26: バッチは製品種別ごとに作る。既定のバッチサイズは 10 修理。

### 5.4 LLM の出力

- G-06: LLM は `{"results": [ ... ]}` の形で、1修理につき次を返す。

```json
{"rec_key": "000123",
 "failures": [
   {"code": "M001", "source": "repair", "excerpt": "power board defective", "excerpt_ja": "電源基板の不良"},
   {"code": "M020", "source": "user",   "excerpt": "LCD flickers",          "excerpt_ja": "液晶がちらつく"}
 ],
 "primary_code": "M001",
 "environment": [{"factor": "impact", "source": "user", "abnormal_use": false, "excerpt": "dropped"}],
 "info_level": "thin"}
```

| 項目 | 内容 |
|---|---|
| `failures` | 記載されている故障の種類(複数可、同じコードは1回)。`source`: `user` / `repair` / `internal` |
| `primary_code` | 主な故障1つ(G-08) |
| `environment` | 使用環境・取り扱いの記述(v2 と同じ。`factor`: `impact` / `water` / `sand_dust` / `heat` / `cold` / `humidity`)。無ければ空の配列 |
| `info_level` | `sufficient`(故障の種類まで読める)/ `thin`(大まかにしか読めない)/ `none`(読めない) |
| `excerpt` | 原文からそのまま抜き出す(原文の言語のまま) |
| `excerpt_ja` | `excerpt` の日本語訳。原文が日本語ならそのまま |

- G-07: ラベルの視点
  - 修理者の所見(修理者コメント・内部コメント)を優先する。
  - 修理者が再現できていなくても、ユーザが故障と認識して申告した内容は `failures` に含める(`source: user`)。再現の有無は判定しない。
- G-08: `primary_code` の選び方
  1. 修理者コメント・内部コメントに故障の所見があれば、その中で最初に書かれたもの
  2. 無ければ、ユーザ申告のうち最初に書かれたもの
  3. どちらも無ければ判定不能コード(このとき `failures` は空、`info_level` は `none`)
  - 「交換部品に最も関係しそうな故障」を LLM に選ばせない。
- G-09: 現認・メーカー責任・代表故障は出力しない。ユーザ申告に「修理者側でも記述があるか」の印も付けない。
- G-13: 定型文だけ(例: "Repaired." "Replaced part.")で何が起きたか読めない修理は判定不能とし、推測させない(プロンプトで指示する)。
  - **交換した部品名だけが書かれていて、現象が書かれていない場合も、部品名から推測しない**(プロンプト初版の判断。実データで判定不能が多すぎる場合は見直す)。
- G-27: プロンプト本文は `prompts/classify_prompt.md`(リポジトリの初期値は `config/prompts/classify_prompt.md`。`init` でローカル作業フォルダにコピーする)で管理し、Dify に貼り付ける。キャッシュの区別(G-16)には、このファイルの SHA-256 を使うため、Dify に貼ったものと同じ内容にしておく。Dify の構築手順は `docs/dify/classify_workflow_setup.md`。プロンプト初版には、G-07・G-08・G-13 の指示と、言語ごとの短い架空の例を入れる。

### 5.5 検証

- G-28: 応答のパースは v2 の R-33 と同じ形(`{"results": [...]}`、配列そのもの、```json で囲まれた文字列)を受け付ける。
- G-29: 各修理の結果を次のとおり検証する。

| 種類 | 内容 | 扱い |
|---|---|---|
| `missing_record` | 結果に含まれない `rec_key` がある | エラー |
| `unknown_code` | コードがその製品種別のコード体系に無い | エラー |
| `invalid_enum` | `source`、`info_level`、`factor` が定義外 | エラー |
| `primary_mismatch` | `primary_code` が `failures` のコードにも判定不能コードにも当てはまらない | エラー |
| `parse_error` | 応答が JSON として読めない | エラー(バッチ内の全修理) |
| `api_error` | Dify の呼び出しに失敗した(E-10 のリトライ後) | エラー(バッチ内の全修理) |
| `excerpt_not_found` | 抜き出しが原文に含まれない(空白の違いは無視) | 警告 |
| `duplicate_code` | `failures` に同じコードが2回ある | 警告(1つにまとめる) |

- E-10: Dify の呼び出しは、タイムアウト・5xx・接続エラーのときに最大3回リトライする(指数バックオフ)。401/403 はリトライしない(v2 の R-53 と同じ)。

### 5.6 分類不可(Dify のエラーが続く修理)

- G-18: Dify のエラーが続き分類できない修理は、**「分類不可」として処理を止めずに先へ進む**。
- G-19: 再試行の流れ
  1. バッチでエラーになった修理だけを、**1件ずつ**送り直す。

## 6. シリアル変換結果の結合

- 方針(2026-11-05 変更): シリアル → 製造年月・ロットの**変換は、別のツールで行う**(要件定義書 `docs/20261105_serial-converter-requirements.md`。変換表を準備できる会社PCで実装する)。この解析プログラムは変換をせず、変換ツールの出力(変換結果ファイル)を、**分類が終わった後のデータに結合する**。
  - 変換の規則(旧 S-01〜S-07)は、変換ツールの SC-21〜SC-35 に移した(欠番)。
- S-10: 変換結果ファイルは、変換ツールの出力 CSV(UTF-8)とする。次の列を使う。
  - 変換ツールが付け足す列(名前は固定): `serial_normalized`、`lot_code`、`lot_order`、`mfg_ym`、`mfg_status`、`mfg_warning`
  - 製品名の列と基準日(受付日)の列。列名は `input_columns.yaml` の `serial_result_model`・`serial_result_reference_date` で指定する。書かなければ、入力 CSV と同じ列名(`model`・`received_date` に指定した列名)とする(解析に使う入力 CSV をそのまま変換した場合は、指定が要らない)。
- S-11: 結合のキーは **製品名 + シリアル + 受付日** とする(修理IDは重複があるため使わない)。
  - 製品名: 前後の空白を除いて比べる。
  - シリアル: こちらは I-06 で正規化した値、変換結果は `serial_normalized` を比べる。
  - 受付日: どちらも I-04 の規則で日付にしてから比べる。
  - このキーにより、入力 CSV をそのまま変換したファイルでも、より大きな修理データをまとめて変換したファイルでも結合できる(変換結果の再利用)。
- S-12: 変換結果ファイルの中で同じキーの行が複数ある場合、変換結果の5列(`lot_code`、`lot_order`、`mfg_ym`、`mfg_status`、`mfg_warning`)がすべて同じなら1つにまとめる。違う行があれば**エラー**とし、結合しない(どのキーかを最初の10件まで表示する)。
- S-13: 変換結果ファイルの検査。次の違反があれば**エラー**とし、結合しない(違反の行をファイルの行番号付きで最初の10件まで表示し、全体の件数も示す)。
  - 必要な列が無い
  - `mfg_status` が変換ツールの定義(SC-34: `ok` / `prefix_only` / `no_serial` / `no_model_type` / `not_in_table` / `invalid`)に無い
  - `mfg_ym` が空でも `YYYY-MM` でもない、`lot_order` が空でも整数でもない
  - `mfg_status` が `ok` なのに `mfg_ym` が空
  - `lot_order` は整数の値を小数で書いたもの(`24312.0` など)は整数として受け付ける
  - 変換結果のシリアルが空の行、基準日が無い・読めない行は、結合に使えないため読み飛ばし、件数を記録する(エラーにはしない)
  - `mfg_warning` の値は検査しない(変換ツールの定義 SC-35 に無い値は、結合の要約で表示する)
- S-14: 結合できなかった修理は `mfg_status = not_converted`(この解析だけで使う値)とする。シリアルが空の修理は、変換結果に関係なく `no_serial` とする。
- S-15: 変換結果ファイルを指定しない場合は、すべての修理を `not_converted` とし、使用期間・ロットの観点は「製造年月の情報なし」と書く(A-13c)。
- S-16: 結合の結果として、`mfg_status` 別の件数、`not_converted` の件数と機種の上位10件、`mfg_warning` 別の件数を表示し、実行メタ情報に記録する。
- S-17: 結合した変換結果ファイルのパスと SHA-256 を実行メタ情報に記録する(O-05)。
- S-18: `mfg_status = prefix_only`(頭桁のみ)のロットは、周期(96 の次が 01 など)があっても区別できないため、レポートに「同じ頭桁に異なる時期の製造が混ざる可能性がある」と注記する。
- S-19: `mfg_warning` がある修理の件数(`after_reference`、`serial_was_number`、`no_reference_date` 別)を、レポートの前提(T-07)に書く。
- S-08: 使用期間(月数)= 受付日の年月 − 製造年月(通し月数の差)。0 より小さいもの、または **96か月** を超えるもの(`usage_max_months`)は使用期間の解析から除き、件数を表示する。
  - 各修理に `usage_months`(月数。製造年月が無ければ空)と `usage_status` を付ける。`usage_status`: `ok`(使用期間の解析に使う)/ `no_mfg_ym`(製造年月が無い)/ `negative`(マイナス)/ `over_max`(上限超え)。上限ちょうど(96か月)は `ok`。

## 7. 解析

### 7.1 共通

- A-01: 製品(機種)× 部番の組み合わせごとに解析する。
- A-02: 判定不能と分類不可は、それぞれ件数と割合を必ず表示し、故障の種類の比較の分母からは除く。全体の構成比の表には、含めた場合の値も参考として並べる。
- A-03: 構成比の基本は `primary_code`(1修理1コード、合計 100%)。補足として `failures` による「その故障が記載された修理の割合」(合計は 100% を超える)も出す。
- A-04: その組み合わせの中で `primary_code` の件数が **5件未満**(`rare_code_min`)のコードは、表示と検定のとき「その他(少数)」にまとめる。まとめる前の件数は別の表に残す。
- A-09: 2つの群の比較方法(全観点で共通)
  - 全体の構成の差: カイ二乗検定(`scipy.stats.chi2_contingency`)。期待度数 5 未満のセルが 20% を超える場合は、結果に「参考」の印を付ける
  - コードごとの差: 2×2 のフィッシャーの正確検定(両側)。同じ比較の中のコードについて Benjamini-Hochberg で補正する
  - 差の大きさとして、割合の差(ポイント)と比を出す
- A-22: 群を比べる表には、群ごとの**販社別の構成**と、**判定不能・分類不可の割合**を並べて出す。
- A-23: 2つの群で、いずれかの販社の割合の差が **20ポイント** 以上(`region_diff_note_pt`)なら、「販社の構成が異なるため、差の一部はそれによる可能性がある」と注記する。

### 7.2 観点1: 全体

- A-05: 故障の種類の構成比(件数・割合)、`failures` による記載割合、環境要因(要因別)の割合、判定不能・分類不可の割合。
- A-05a(2026-11-05 追加): 全体の**偏りの大きさ**を数字で示す(検定はしない)。主な故障(まとめる前のコード)で数える。
  - 最も多い故障の種類とその割合、上位3つの割合、全体の80%になるまでの故障の種類の数、故障の種類の数
  - 文章: 「最も多い『○○』が全体の xx%、上位3つで yy% を占めます。全体の80%は n 種類の故障で占められます」
  - 最も多い故障の種類の割合が **50%** 以上(`concentration_high_pct`)なら「特定の故障の種類(『○○』)に修理が集中しています」、**30%** 未満(`concentration_low_pct`)なら「特定の故障の種類への偏りは小さいです」を加える。その間は数字だけを示す。
  - 分類できた修理が `min_group_n` 件未満なら、「割合は参考値です」と注記する。
  - `tables.xlsx` の「偏りの指標」シート、`index.xlsx` の列(最も多い故障・その割合・上位3つの割合)、`findings.json` の `concentration` にも出す。
- A-06: 販社別の件数と、販社別の故障の種類の構成比。
- A-19: 同じシリアルが入力内に2回以上ある件数(再修理の可能性)。シリアルの一覧は表に出す。

### 7.3 観点2: 最近の修理 vs それ以前

- A-07: 基準日は**実行日**。既定は「実行日から直近 **6か月**(`recent_months`)」と「それ以前」を比べる。
  - 直近の期間は、実行日の月を含めず、前月までの6か月とする(当月は途中のため)。例: 実行日 2026-11-05 → 直近は 2026-05〜2026-10
  - データ中の最新の受付日が、直近期間の最終月より前の月なら、警告を表示する(抽出日が古い可能性)
  - 実行日の月以降の受付(と、`same_length` のときは比べる期間より前の受付)は比較に含めず、件数を注記する
- A-08: 比較対象は既定で「それ以前すべて」(`recent_compare: all_before`)。`same_length` にすると、直前の同じ長さ(6か月)と比べる。
- A-10: 月ごとの件数と、月ごとの故障の種類の構成(時系列の表)。

### 7.4 観点3: 使用期間

- A-11: 使用期間の区切りは 0〜6か月 / 7〜12 / 13〜24 / 25〜36 / 37か月以上(`usage_bins`)。
- A-12: 出力する表
  - 使用期間の分布(区切りごとの件数・割合、中央値・四分位)
  - 故障の種類ごとの使用期間(件数、中央値・四分位)
  - 区切り × 故障の種類のクロス表(構成比)
- A-13: 「**12か月以内**」(`early_months`)と「それ以降」で故障の種類の構成を比べる(A-09)。
- A-13a: レポートに「使用期間は製造年月からの期間で、製造から販売までの在庫期間を含む(購入日からではない)」と書く。
- A-13c: 製造年月が求められなかった修理は、この観点から除き、`mfg_status` 別の件数を表示する。製造年月が求められた修理が無い場合は、観点ごと「製造年月の情報なし」と書く。

### 7.5 観点4: 製造ロット

- A-15: `lot_code` ごとに、件数・割合と故障の種類の構成比を、製造の順(`lot_order`)に並べた表を出す。
- A-15a: 生産台数のデータが無いため、注目点の判定は**構成比の偏り**で行う。
  - 各ロットについて、コードごとに「そのロット」と「他のロットすべて」を 2×2 のフィッシャーの正確検定で比べる。補正(Benjamini-Hochberg)は、**検定したすべてのロット × コードをまとめて**行う(2026-11-05 変更。ロットが多いと、ロットごとの補正では偶然の差を注目点にしやすいため)。
  - ロットは「製造の順 + 頭桁」で分ける(周期のある方式で、同じ頭桁でも製造年月が違えば別のロット)。表示名は製造年月があれば「YYYY-MM(頭桁 xx)」、無ければ「頭桁 xx」。
  - 件数の偏りは**参考扱い**とし、注目点(A-14)に含めない: 修理のあるロットを製造の順に並べ、前後 **3ロット**(`lot_neighbor`)の件数の中央値の **2倍** 以上(`lot_spike_ratio`)、かつ `lot_min_n` 件以上のロットに「参考」の印を付ける。文章では「生産台数のデータがないため、件数の偏りが生産量によるものかは判断できない」と必ず添える。
- A-15b: 頭桁のみのロットも、頭桁の順を製造の順として隣接の比較を行う(S-18 の注記を付ける)。
- A-15c: 件数が **5件未満**(`lot_min_n`)のロット(A-15d のまとまりも同じ)は、検定と件数の偏りの判定から除く(表には出す)。
  - 5件のロットで注目点になるのは、ほぼすべてが同じ故障の場合に限られる(他のロットでの割合が 10% 程度のとき、5件中4〜5件)。少ないロットの偏りは、A-15d のまとまりで見る。
- A-15d(2026-11-05 追加): 製造の順で隣り合う **3ロット**(`lot_window`)を1つのまとまりにし、まとまりごとに「そのまとまり」と「他のロットすべて」を比べる(方法は A-15a と同じ)。
  - 1ロットごとの比較(A-15a)と、まとまりの比較の**両方**を行う。補正は、1ロットごとの比較・まとまりの比較のそれぞれの中で、まとめて行う。
  - まとまりは製造の順の値で区切る(製造年月があれば暦の3か月ずつ、頭桁のみなら頭桁の値3つずつ)。修理の無い月・頭桁も1つと数える。区切りは、修理のあるロットのうち最も古いものから始める。
  - ロットが1つしか入らないまとまりは比べない(1ロットの比較と同じになるため)。
  - 表示名は、製造年月があれば「YYYY-MM〜YYYY-MM」、無ければ「頭桁 xx〜yy」。
  - `lot_window` を 1 にすると、まとまりの比較はしない。
  - 区切りの境目で偏りが2つのまとまりに分かれる場合は、拾いにくくなる(区切りをずらして重ねる方法は、検定の回数が増えるため採らない)。
- A-24: ロットごとの使用期間の中央値を表に並べ、「古いロットほど市場での期間が長い」と注記する(製造年月があるロットのみ)。

### 7.6 注目点

- A-14: 次の条件を**すべて**満たした差だけを「注目点」とする。
  1. 比べる2つの群の件数がどちらも **30件以上**(`min_group_n`)。ロットの比較では、そのロット(まとまり)が `lot_min_n` 以上、他のロットが `min_group_n` 以上
  2. 補正後の p 値 < **0.05**(`alpha`)
  3. 割合の差が **10ポイント以上**(`min_diff_pt`)、かつ、割合が高い側の群でそのコードの件数が **5件以上**(`min_code_n`)
  - 「その他(少数)」は複数のコードの寄せ集めのため、注目点にしない。
  - 件数は、判定不能・分類不可を除いた件数で数える。
- A-14a: 条件1を満たさない比較は「件数が少なく判断できない」、条件1を満たし 2・3 を満たさないものは「目立った差は見られない」と分類する。
- A-14b: 注目点は JSON(`findings.json`)に出力する。項目: `aspect`(`recent` / `usage` / `lot`)、`group_a`・`group_b`(名前と件数)、`code`・`name`、両群の件数と割合、差(ポイント)、比、補正後の p 値、`notes`(A-23、S-18、A-24 などの注記)。比較ごとの判定結果(注目点あり/差なし/件数不足)も入れる。

    - 件数不足: 「直近6か月の件数が 12件と少ないため、比較による判断はできません。」
    - 注目点: 「直近6か月では『○○』の割合が 28%(15/52件)で、それ以前の 9%(28/310件)より 19ポイント高くなっています。」
  - 層2(任意): Dify(要約用ワークフロー)で、`findings.json` と層1の文を入力に、読みやすい要約(400字程度)にまとめる。`DIFY_API_KEY_SUMMARY` が無い、または U-03 で n を選んだ場合は作らない。
    - 要約は report.md の「前提」の前に「要約(Dify による文章)」として入れる(定型文は変えない)。目印のコメントで囲み、作り直し(`--force`)のときは置き換える。
    - Dify の呼び出しに失敗した組み合わせは、report.md を変えずに件数を示す。
    - コマンド `summarize --run <実行フォルダ>` でも作れる。要約用プロンプトは `prompts/summary_prompt.md`、Dify の構築手順は `docs/dify/summary_workflow_setup.md`。
- T-03: 要約用プロンプトの指示: 入力にない数値を書かない/原因を推測しない(注記にある可能性以外は書かない)/注目点が無ければ無いと書く/件数不足は「判断できない」と書く。
- T-04: 「増加」「多発」などの語は使わず、「割合が高い」「構成比が異なる」と書く(定型文・プロンプトとも)。
- T-05: 層2の文に含まれる数値(整数・小数・%)が、`findings.json` と層1の文の数値に含まれるかを照合し、含まれないものは警告としてレポートの末尾(「要約の確認」)に一覧で示す。T-04 の使わない約束の言葉が要約文にあった場合も、同じ場所に示す。
- T-06: 説明文は日本語。
- T-07: レポートの冒頭に、前提を定型文で書く: 件数(入力・除外・判定不能・分類不可)、受付日の期間、実行日、製造年月・ロットが求められた割合(`mfg_status` 別)と `mfg_warning` の件数(S-19)、内部コメントを渡さなかった販社、海外データの分類精度は正解データで検証していないこと、生産台数のデータが無いこと。
- T-08: 注目点ごとに代表事例を **3件**(`examples_per_finding`)、原文と日本語訳(`excerpt` / `excerpt_ja`)で示す(たたき台の A-20)。抽出は乱数の種を固定する。
  - 代表事例は、比べた群(直近の期間・使用期間の短い側・そのロット)で割合が**高い**注目点にだけ示す。低い注目点は、構成比の影響(ある故障が多いと、ほかの故障の割合が下がる)のことが多いため。
  - 同じ比較の中に、高い注目点と低い注目点の両方がある場合は、構成比の影響についての注記を付ける(T-02)。
  - 主な故障がそのコードの修理を優先し、足りなければ、そのコードが記載された修理から選ぶ。

## 10. 実行方法

- U-01: 修理データを渡せば、画面の質問に y / n で答えていくだけで、解析の出力まで進められるようにする。
- U-02: 起動は `python anomaly_cli.py`(サブコマンドなしで対話式)。入力ファイルのパスは起動後に聞く。パスの前後の引用符(ドラッグ&ドロップで付くもの)は取り除く。
  - ローカル作業フォルダは `--local-dir`、環境変数 `ANOMALY_LOCAL_DIR`、起動後の質問の順で決める。フォルダが無ければ、`init` で作るよう案内して終了する。
  - 実行フォルダは、段階0で新しく始めるときに `<ローカル作業フォルダ>/outputs/{timestamp}/` に作る。
- U-03: 段階と質問

| 段階 | 表示する内容 | 質問 |
|---|---|---|
| 0. 再開の確認 | 途中で終わった実行があれば、日時と段階 | 「前回の続きから再開しますか?(y/n)」n なら新しく始める |
| 1. 入力の確認 | 件数、列の対応づけ、足りない列、除外の件数(理由別。受付日・製品種別は値の例。I-05a)、組み合わせの数と一覧(上位10件)、販社別・言語別の件数、修理IDの重複件数 | 「この内容で進めますか?(y/n)」 |
| 2. 分類の準備 | キャッシュ済みの件数、Dify に送る件数、呼び出し回数と所要時間の目安(1回30秒として)、内部コメントを渡さない販社 | 「分類を始めますか?(y/n)」 |
| 3. 分類 | 進み具合(何件中何件)。終了後に ok / 判定不能 / 分類不可 の件数 | 分類不可が G-22 の閾値を超えたら「1: 再試行する 2: このまま解析に進む 3: 中断する」 |
| 4. シリアル変換結果の結合 | 変換結果ファイルのパスを聞く(Enter で飛ばす。S-15)。結合の結果(S-16) | 「この内容で解析に進みますか?(y/n)」 |
| 5. 解析の設定 | 主な既定値(直近の期間、比較の方法、使用期間の区切り、注目点の閾値) | 「この設定で解析しますか?(y/n)」n なら項目ごとに値を聞き直す(Enter でそのまま) |
| 6. 解析 | 組み合わせごとの判定(注目点の数) | ー |
| 7. 説明文 | 定型文は常に作る。要約を作った場合は、作った件数・警告のあった件数 | 「Dify で要約文も作りますか?(y/n)」(`.env` に `DIFY_API_KEY_SUMMARY` がある場合のみ) |
| 8. 完了 | 出力フォルダのパスと、ファイルの一覧 | ー |

- U-04: n を選んだ段階で終了する。それまでの結果は実行フォルダに保存し、`state.json` に段階を記録する。次回の起動時に段階0で再開を選べる。
  - 再開の対象は、`outputs/` の中で `state.json` が「完了」でない実行のうち、いちばん新しいもの。
  - 分類(段階3)の前に終わった場合: 再開すると段階1から(入力ファイルは覚えているので聞き直さない)。分類済みの修理はキャッシュから使う。
  - 分類の後に終わった場合: 再開すると、終わった段階の次から(分類済みのデータを実行フォルダから読む。Dify は呼ばない)。
  - 再開しない(n)を選ぶと、新しい実行フォルダで始める。
  - 段階3の「中断する」を選んだ場合は、分類の前に終わった扱いにする(分類できた修理はキャッシュに残る)。
- U-05: 途中で止まっても(Ctrl+C、PC のスリープ、Dify の長い障害)、分類済みの修理はキャッシュに残り、再開時は分類の続きから処理する。キャッシュへの書き込みはバッチごとに行う。
- U-06: 質問なしで最後まで進める: `python anomaly_cli.py run --input <CSV> [--serial-result <CSV>] --yes`。段階3で閾値を超えた場合は「このまま解析に進む」を選ぶ。`--serial-result` が無ければ、シリアル変換結果は飛ばす。設定は `settings.yaml` と引数で渡す。`--yes` のときは、再開の確認はしない(いつも新しく始める)。
- U-07: 段階ごとの個別コマンドも用意する: `init`、`check`(設定ファイルの検査)、`merge-serial`(入力 CSV とシリアル変換結果の結合だけを試す。分類はしない)、`classify`、`analyze`(分類済みのデータ(O-01 の3つの CSV)から解析・レポートを作る。`--run-date` で基準日を指定できる)、`summarize`(T-02 層2)、`evaluate`(G-15)、`compare-runs`(G-30)、`codes-export` / `codes-import`(v2 と同じ)。
- U-08: 画面には短い要約だけを出し、詳しい内容(画面に出したもの・質問と答え)は実行フォルダの `run.log` に書く。y / n 以外の入力は聞き直す。エラーで止まる場合は、原因と対処を1〜2行で表示する(Windows 側で人がメモしやすいように。v2 の R-56〜R-57 と同じ考え方)。
- U-09: `check` では、コード体系(v2 の R-16 と同じチェック)、`input_columns.yaml`、`settings.yaml` の値の範囲を検査する(シリアル変換表の検査は、変換ツールの `check` で行う)。
