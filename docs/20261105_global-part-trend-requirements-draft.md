## 0. 前提(リポジトリで確認したこと)

このフォルダは v2(LLM方式)一式のコピーで、次を確認した。

- 入力列: `repair_id`, `product_type`(事業コード), `user_comment`, `repair_comment`, `internal_1`, `internal_2`(`config/input_columns.yaml`)

- Dify 呼び出し、応答のパース・検証・再試行、実行メタ情報、ローカル作業フォルダの仕組みは製品・言語に依存しない

## 1. 目的と全体像

### 1.1 目的

部品の使用率による異常検知で抽出された「製品(機種)× 部品番号」の修理データについて、故障の種類の傾向を、

1. 全体
2. 最近の修理 vs それ以前(受付日)
3. 使用期間(受付日 − 製造年月)
4. 製造ロット(製造年月またはシリアル頭桁)への集中

の観点で集計し、表と中立的な説明文(日本語)で示す。異常がなければ「目立った差はない」と書くことを正しい結果とする。

- 【確定】製造時期(最近製造 vs それ以前)の比較は行わず、使用期間の解析に置き換える。
- 【確定】特定ロットへの集中は確認する(5.6)。
- 規模の目安【確定】: 1回の解析で数千件。

### 1.2 全体の流れ【案】

```
[入力CSV: 修理データ(全世界)。製品×部番で抽出済み、1行=1修理]
  ↓ (1) 読み込み・列の対応づけ・内部キー付与・言語判定・空欄判定   Python
  ↓ (2) 分類(キャッシュに無い修理だけ Dify へ)                  Python + Dify  ← 会社PC
[分類結果(修理単位)] ← 分類キャッシュに蓄積
  ↓ (3) 製造年月・ロット・使用期間の付与(シリアル変換表)        Python
  ↓ (4) 製品×部番ごとに集計・比較・注目点の判定                   Python(決定的)
[表(Excel/CSV) + 注目点リスト(JSON)]
  ↓ (5) 説明文の作成                                             Dify(LLM)または定型文  ← 会社PC
[レポート]
```

ポイント: **「何が注目点か」は Python がルールで決め、LLM は文章化だけを担う**(第6節)。LLM に生データから異常を探させない。

## 3. 分類部の要件案

### 3.1 対象と言語

- G-01【ユーザ指定】日本語・英語・中国語・韓国語のコメントを分類できること。
- G-02【案】言語は Python で文字種から判定し(ハングル→ko、かな→ja、漢字のみ→zh、それ以外→en など)、結果に `lang` 列として残す。解析で「言語・地域による書き方の差」を区別するために使う(A-22)。
- G-03【案】コード一覧は日本語のまま LLM に渡す。多言語の入力を日本語のコードに正しく対応づけられるかは**未確認**(G-14)。

### 3.2 日本と海外の区別

- G-04【ユーザ指定】販社名の列で日本と海外を区別できる。日本の販社は CMJ。
- G-05【確定】日本のデータも、海外と**同じ全世界用プロンプト**で分類する。

### 3.3 1修理あたりの出力(ラベル)

丸数字が無く、記載も薄いため、v2 の「申告ごとの行」はやめ、**修理単位で故障の種類の集合**を出す。

- G-06【案】LLM の出力(1修理あたり)

```json
{"rec_key": "000123",
 "failures": [
   {"code": "M001", "source": "repair", "excerpt": "power board defective", "excerpt_ja": "電源基板の不良"},
   {"code": "M020", "source": "user",   "excerpt": "LCD flickers",          "excerpt_ja": "液晶がちらつく"}
 ],
 "primary_code": "M001",
 "environment": [{"factor": "impact", "source": "user", "abnormal_use": false, "excerpt": "dropped"}],
 "info_level": "thin"}
```

| 項目 | 内容 |
|---|---|
| `rec_key` | 内部キー(I-02)。LLM には修理IDではなくこれを渡す |
| `failures` | 記載されている故障の種類(複数可、重複なし)。`source` はどのコメントから読んだか: `user` / `repair` / `internal` |
| `primary_code` | 主な故障1つ。集計の基本単位(A-03) |
| `environment` | 落下・水濡れなどの記述(v2 と同じ)。部品の傾向が「落下品の増加」で説明できるかを見るため |
| `info_level` | `sufficient`(種類まで読める)/ `thin`(大まかにしか読めない)/ `none`(読めない) |
| `excerpt` | 原文から抜き出し(原文の言語のまま) |
| `excerpt_ja` | `excerpt` の日本語訳(日本語の原文はそのまま)。G-14 の目視確認と、レポートの代表事例(A-20)に使う |

- G-07【確定】ラベルの視点
  - **修理者の所見を優先**する。
  - ただし、修理者が再現できていなくても、**ユーザが故障と認識して申告した内容は `failures` に含める**(`source: user`)。再現の有無は判定しない。
  - 修理者コメントで「異常なし」「再現せず」とされた申告も、ユーザが申告した故障として残す。
- G-08【案】`primary_code` の選び方
  1. 修理者コメント・内部コメントに故障の所見があれば、その中で最初に書かれたもの
  2. 1 が無ければ、ユーザ申告のうち最初に書かれたもの
  3. どちらも無ければ判定不能コード
  - 「交換部品に最も関係しそうな故障」を LLM に選ばせることはしない(推測になるため)。
- G-09【ユーザ指定】現認(再現)・メーカー責任 YES/NO・代表故障は出力しない。環境要因は残す(G-06)【案】。
- G-09a【確定】ユーザ申告の故障に「修理者側でも記述があるか」の印は付けない。

### 3.4 空欄・内容の薄さ・内部コメント

- G-10【ユーザ指定】ユーザ・修理者・内部1・内部2 のいずれかが空欄なのは普通のこととして扱う。
- G-11【案】LLM に渡すコメントがすべて空欄の修理は **LLM に送らず**、Python で判定不能コード(`role: unknown`)・`info_level: none` にする。
- G-12【確定】内部コメントは LLM に**渡す**。ただし、販社ごとに「渡さない」を選べるようにする。
  - 【確定】設定ファイルに「内部コメントを渡さない販社」の一覧を持つ。**既定値は `[CMJ]`**(日本は渡さない。修理に関係しない記載が多く長いため)。
  - 一覧を変えれば、CMJ にも渡す・他の販社でも渡さない、を選べる。
  - 【案】切り替えの判断材料として、日本のデータで「渡す/渡さない」の両方で分類し、`primary_code` の一致率と判定不能の割合を比べる手順を用意する。
- G-13【案】定型文だけ(例: "Repaired." "Replaced part.")で何が起きたか読めない修理は判定不能コードとし、無理に推測させない(プロンプトで明示)。

### 3.5 精度確認

- G-14【確定】海外データの正解データは**準備しない**(時間がないため)。
  - 【案】代わりに次で確認する。
    1. **目視の抜き取り確認**: 言語ごとに 20 件程度を無作為に抜き出し、原文・`excerpt_ja`・付いたコードを1表にした確認用 Excel を出力する。人は「明らかにおかしいもの」に印を付けるだけ(正解は作らない)。訳が誤っている可能性は残る。
    2. **言語別の機械的な指標**: 言語別に、判定不能の割合、`info_level` の分布、`failures` の平均件数、`excerpt` が原文に見つからない割合を出す。極端に偏っている言語は、分類がうまくいっていない可能性がある。
    3. **日本データでの評価**: 日本は過去の分類結果があるため、v2 の `evaluate` の考え方で一致率を見る。ただし過去の結果は「メーカー責任の代表故障」なので、定義の違いを踏まえて参考値とする。
  - 【案】レポートの冒頭に「海外データの分類精度は正解データで検証していない」と明記する(T-07)。
- G-15【案】評価コマンドは、日本データについて修理単位の `primary_code` 一致率と、`failures` の集合の一致率(適合率・再現率)を出す。

### 3.6 規模と再利用

- G-16【案】分類結果を**キャッシュ**(CSV)する。キーは「販社名 + 修理ID + 受付日 + LLM に渡したコメントのハッシュ」(修理IDだけでは重複があるため、I-02)。コード体系・プロンプト・内部コメントの設定が変わったら、別のキャッシュとして扱う。
- G-17【確定】件数は1回あたり数千件。【案】既定のバッチは 10 件(数百回の呼び出し)。数千件なら `--resume` とキャッシュで中断・再開に対応すれば十分で、並列化は当面しない。

### 3.7 Dify のエラーが続く修理の扱い【ユーザ指定・2026-11-05】

- G-18【ユーザ指定】Dify に渡して何度もエラーになり分類できない修理は、**「分類不可」として処理を止めずに先へ進む**。
- G-19【案】再試行の流れ(v2 の R-35〜R-36 を拡張)
  1. バッチ(10件)の呼び出しが失敗した、または応答の一部がエラー(JSON として読めない、件数が合わない、定義外のコード等)の場合、エラーの修理だけを**1件ずつ**送り直す。
  2. 1件ずつの送り直しは最大 **2回**(設定で変更可)。通信エラー(タイムアウト・5xx)のリトライ(R-53、最大3回)はこれとは別に行う。
  3. それでもエラーの修理は `classify_status = failed`(**分類不可**)とし、`failed_reason`(`api_error` / `parse_error` / `invalid_output` など)を記録して次へ進む。
- G-20【案】「分類不可」と「判定不能」は**別のもの**として扱う。
  - 判定不能: LLM が読んだが、コメントから故障の種類が読み取れない(データの問題)
  - 分類不可: システムの都合で分類結果が得られなかった(Dify の問題)
  - 分類不可の修理には専用の値(例: `primary_code = CLASSIFY_FAILED`)を入れ、コード体系のコードとは混ぜない。
- G-21【案】解析での扱い: 分類不可は、判定不能と同じく**比較の分母から除き、件数と割合を必ず表示**する(A-02)。使用期間・ロットの件数の集計(故障の種類を使わない表)には含める。
- G-22【案】分類不可が多い場合の歯止め: 分類不可の割合が閾値(既定 5%)を超えたら、解析に進む前に警告し、「再試行する / このまま解析に進む / 中断する」を選ばせる(第7.1節)。
- G-23【案】分類不可の修理はキャッシュに保存しない(次回の実行で自動的に再試行の対象になる)。一覧を `classify_failed.csv`(rec_key、修理ID、販社、理由)に出力する。
- G-24(欠番)【確定】エラーは Dify 側の要因で、こちらでは対策できないことが分かっているため、送る内容を変える対策(切り詰め・内部コメントを外す等)は行わない。再試行して駄目なら分類不可とする。

## 5. 解析部の要件案

### 5.1 集計の基本

- A-01【ユーザ指定】製品(機種)×部番の組み合わせごとに解析する。
- A-02【案】判定不能(`info_level: none`)と分類不可(G-20)は、それぞれ**件数と割合を必ず表示**し、比較の分母からは除く(含めた場合の値も参考に出す)。
- A-03【案】構成比の基本は `primary_code`(1修理1コード、合計100%)。補足として `failures` による「その故障が記載された修理の割合」(複数該当、合計は100%を超える)も出す。
- A-04【案】件数の少ないコードは、表示上「その他(少数)」にまとめる(例: 全体で5件未満)。統計的な比較もまとめた後のカテゴリで行う。

### 5.2 観点1: 全体の傾向【ユーザ指定】

- A-05 故障の種類の構成比(件数・割合)、環境要因(落下・水濡れ等)の割合、判定不能の割合。
- A-06【案】販社(または地域)別の件数と構成比。どの地域の修理が多いかで全体の構成が決まるため。

### 5.3 観点2: 最近の修理 vs それ以前(受付日)【ユーザ指定】

- A-07【確定】比較の基準日は**実行日**。【案】既定: 実行日から直近6か月 vs それ以前。期間は引数で変えられる。
  - 【案】データの抽出日が実行日より古い場合、直近の件数が少なく見える。直近期間の最新受付日と実行日の差が大きい(例: 1か月以上)ときは警告を表示する。
- A-08【案】直近の比較対象を「それ以前すべて」ではなく「その前の同じ長さ(6か月)」にする選択肢も持つ。古い期間が長いと、製品のライフサイクル(発売直後/末期)の違いが混ざるため。
- A-09【案】比較の方法(`scipy` を使う【確定: 使用可】)
  - 全体: カイ二乗検定(期待度数が小さい場合はカテゴリをまとめる)
  - コードごと: 2×2 のフィッシャーの正確検定 + 多重比較の補正(Benjamini-Hochberg)
  - あわせて差の大きさ(割合の差[ポイント]、比)を出す。**p値だけで注目点にしない**(A-14)。
- A-10【案】月ごとの件数と構成の推移(時系列の表)も出す。

### 5.4 観点3: 使用期間(受付日 − 製造年月)【確定】

製造年月はシリアルから求める(5.5)。

- A-11【案】使用期間を月数で計算し、期間帯に分ける。既定の区切り: 0〜6か月 / 7〜12 / 13〜24 / 25〜36 / 37か月以上(設定で変更可)。
- A-12【案】出力する表
  - 使用期間の分布(期間帯ごとの件数・割合、中央値・四分位)
  - 故障の種類ごとの使用期間(中央値・四分位・件数)。初期に出る故障か、長く使った後に出る故障かが分かる
  - 期間帯 × 故障の種類のクロス表(構成比)
- A-13【案】比較: 「初期(既定 12か月以内)」と「それ以降」で故障の種類の構成を比べる(方法は A-09 と同じ)。
- A-13a【案】使用期間には**製造から販売までの在庫期間が含まれる**(購入日ではない)ことをレポートに明記する。
- A-13b【案】使用期間がマイナス、または極端に長い(例: 96か月超。周期のある方式では判別できないため)ものは除外し、件数を表示する。
- A-13c【案】シリアルが無い・変換できない修理は、この観点から外し、件数と割合を表示する。製品自体に変換方法が登録されていない場合は、観点ごと「製造年月の情報なし」と書く。

### 5.5 シリアル → 製造年月・ロットの変換【確定(方式)】

機種ごとの「製造年月のタイプ」を表で持ち、タイプごとの規則で変換する。既知は3タイプ。ほかにもある可能性があるため、タイプを後から足せる作りにする。

- A-30【案】設定ファイル(ローカル作業フォルダに置く。Windows 側で人が作る)

| ファイル | 列 | 内容 |
|---|---|---|
| `serial_model_types.csv` | `model`, `serial_type`, `start_ym`(タイプ3のみ) | 機種ごとのタイプ |
| `serial_type1_prefix3.csv` | `prefix3`, `ym` | タイプ1: 頭3桁 → 製造年月 |
| `serial_type2_cycle.csv`(または設定値1つ) | 周期の起点(01にあたる年月) | タイプ2: 全機種共通の起点 |

- A-31 タイプ1【確定】: シリアル頭3桁で製造年月が決まる。対応表は後日。
  - 【案】頭3桁 → 製造年月(YYYY-MM)の表引き。
- A-32 タイプ2【確定】: シリアル頭2桁(01〜96)。1つ進むと1か月。96の次は01に戻る(8年周期)。周期の起点は全機種共通。
  - 【案】候補 = 起点 + (頭2桁 − 1)か月 + 96か月 × k。**受付日以前で受付日に最も近い候補**を製造年月とする。
- A-33 タイプ3【確定】: シリアル頭2桁(01〜96)。製造開始の月を01とし、1つ進むと1か月。01にあたる年月は機種ごと。96の次は01に戻る(周期する機種はまれだがある)。
  - 【案】候補 = 機種の `start_ym` + (頭2桁 − 1)か月 + 96か月 × k。選び方はタイプ2と同じ。
- A-34【案】変換の結果として、各修理に次を付ける。
  - `mfg_ym`(製造年月。求められない場合は空)
  - `lot_code`(ロットの識別子。年月が求められない場合も頭桁で付ける。A-36)
  - `lot_order`(製造の順を表す番号。年月があれば年月から、頭桁のみなら頭桁の数字から)
  - `mfg_status`: `ok` / `prefix_only`(頭桁は分かるが年月が求められない)/ `no_serial` / `no_model_type` / `not_in_table` / `invalid`
- A-35【案】変換部は Dify と無関係なので、Mac 側で架空の表を使って作り込み・テストする。実際の表は Windows 側で作る。
- A-36【確定】シリアルの頭桁(2桁・3桁)で製造ロットは分かるが、年月までは計算できない機種にも対応する。
  - 【確定】頭桁のみのタイプでも、**頭桁の数字の順は製造の順**になっている。
  - 【案】`serial_model_types.csv` に、年月の規則を持たない「頭桁のみ」のタイプ(例: `prefix2_only`、`prefix3_only`)を設ける。この場合 `lot_code` = 頭桁、`lot_order` = 頭桁の数字、`mfg_ym` は空。使用期間の解析(5.4)からは外し、ロットの解析(5.6)には使う。
  - 【案】頭桁のみのタイプで周期(96の次が01)がある機種は、年月が無いと周期を区別できない。この場合 `lot_order` は周期内の順として扱い、レポートに「周期を区別できないため、同じ頭桁に異なる年の製造が混ざる可能性がある」と注記する。
  - 【案】機種がタイプ表に無い場合の既定動作は「変換しない(`no_model_type`)」。頭桁で自動的にロットを推測することはしない(誤ったロット分けを防ぐため)。

### 5.6 観点4: 製造ロットへの集中【確定】

- A-15【案】`lot_code` ごとに次を出す。
  - 件数、全体に占める割合
  - ロットごとの故障の種類の構成比
  - 製造の順(`lot_order`)に並べた表
- A-15a【確定】生産台数のデータは**渡せない**。そのため、ロットごとの件数だけでは「集中」と言えない(件数は生産台数と市場に出てからの期間に左右される)。注目点の判定は次のとおりとする。
  - **構成比の偏り(注目点の対象)**: あるロットで特定の故障の割合が、他のロットと比べて高い(方法は A-09 と同じ。ロット × 故障の種類)。生産台数に依存しない。
  - **件数の偏り(参考扱い)**: 製造の順で隣接するロット(前後数ロット)と比べて件数が突出している場合は、表に「参考」の印を付ける。文章では「生産台数のデータがないため、件数の偏りが生産量によるものかは判断できない」と必ず添える。注目点(A-14)には含めない。
- A-15b【確定】頭桁の順は製造の順のため、頭桁のみのロットでも隣接比較を行う(周期の注記は A-36)。
- A-15c【案】件数が少ないロット(例: 10件未満)は、比較の対象から外すか、隣接ロットとまとめる。

### 5.8 交絡への注意【案】

- A-22 期間・使用期間・ロットで比較するとき、**地域の構成**と**判定不能の割合**も並べて表示する。例: 直近6か月は記載の薄い地域の修理が多く、判定不能が増えた、というだけの差を「傾向の変化」と誤読しないため。
- A-23 地域構成が大きく違う場合は、「地域構成が異なるため、差の一部はそれによる可能性がある」と注記する(ルールで判定)。
- A-24【案】ロットの比較では、古いロットほど市場での期間が長い点も注記する(使用期間の分布をロットごとに並べる)。

### 5.9 注目点の判定(決定的なルール)

- A-14【案】次の条件を**すべて**満たしたものだけを「注目点」とする。満たさないものは表には出すが、文章では「目立った差は見られない」とまとめる。
  - 両群とも件数が最低数以上(例: 各30件以上。ロットの比較は A-15c)
  - 補正後の p 値 < 0.05
  - 差の大きさが閾値以上(例: 割合の差 10ポイント以上、かつ該当件数 5件以上)
  - 閾値は設定ファイルで変えられる。
- 注目点は JSON(観点、コード、両群の件数・割合、差、p値、注記)として出力し、これだけを説明文の材料にする。
